Trash

Every state the screen can be in, drawn at device size in both themes. Option A, built from the components that already exist: a row here is StatementEntry with captionColor and amountDim set — no new element, no second design system.

The governing constraint is the one the whole app is built on: a row is a printed statement line. Fixed pitch, amount flush right in the shared column, hairline between entries. Everything Trash needs to say beyond that has to fit in the caption, and it does — category, day, and time remaining.

1 · Empty — and this is the normal state

Worth designing first, because it is what the household will see almost every time. The ledger holds 446 tombstones from dedupe repairs and none of them belong here, so Trash opens empty and stays empty until somebody deletes something on purpose. An empty screen that only says "nothing here" reads as a feature that is broken or pointless; this one says what the room is for, so the first visit teaches the thirty days.

2 · Holding entries

One row per entry. The caption carries category · day · time left, and the count sits in the tape header where every other list in the app puts it. The amount is dimmed because a deleted row is in no total — the same treatment Activity gives an untagged row, for the same reason.

Colour is never the only signal. "2 days left" is red and says two; "13 days left" is amber and says thirteen. Twelve categories inside one lightness band already collapse under deuteranopia, and the rule that saved that — always print the words — applies here too.

3 · Choosing several

The header becomes the action bar, exactly as Activity's does: the wordmark is replaced by 2 SELECTED in accent and the action sits on the right. That is a pattern the household has already learnt for bulk delete — this is the same gesture pointed the other way, so there is nothing new to learn and no second selection idiom in the tree.

A chosen row is tinted and marked at its left edge — no checkbox column. That is not a style preference: TransactionListRow already made this call and wrote down why. A checkbox pushes every merchant, time and amount sideways the instant selection begins, so the list you were reading rearranges itself under your thumb at exactly the moment you were aiming at something. This screen inherits that rather than re-litigating it. Back clears the selection before it leaves the screen — the same BackHandler guard Activity uses, because leaving with a selection open is how a bulk action gets aimed at rows the reader has forgotten about.

The specification

ElementSpec
Row StatementEntry, Modifier.padding(horizontal = 15.dp) — the inset every other list passes and the shipped Trash did not, which is why its amount ran off the edge of the display.
Caption "${category.label} · ${d MMM} · ${expiryLabel}" through MicroLabel. Day, not clock time: "7:25 pm" for something deleted last week answers a question nobody asked.
Caption colour Ours.textLabel · Ours.warning at ≤ 14 days · Ours.negative at ≤ 3. The same escalation Activity already uses for an untagged row, and the words carry it independently.
Amount amountDim = true, always. Shared right-hand column, tabular figures, no ₹ per row — the column is the unit.
Header TRASH → N SELECTED in Ours.accent with a Put back action, mirroring Activity's selection header.
Empty Two lines, not one: what is here, then what the room is for. It is the state the household will see most often.
Order Newest deletion first — ORDER BY deletedAt DESC. What you just deleted by mistake is what you came for; the thing expiring in two days you were told about by its colour.
Selected row TransactionListRow(selected = true) — accent tint at 14% plus a 3dp left strip. No checkbox column, so nothing moves sideways when selection starts.
Talkback Back carries "Clear selection" while a selection is open, rather than the wrong label or none. Trash is a screen of consequential choices and the wrong place to be silent.
Motion A restored row leaves with the list's default item animation. Nothing bespoke — a bin that animates elaborately is a bin drawing attention to itself.

One thing outside this screen

The delete confirmation still reads "It goes from both phones and cannot be brought back." True when it was written; false twice over now, with an Undo on the way out and thirty days in here. It should say what actually happens — a confirmation that overstates the damage is one people learn to dismiss unread, which costs exactly the protection it was added for.
